# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project: Myr Language

Myr is a systems/game-development language — Rust's algebraic type system + Odin's data-layout awareness, no borrow checker, FP ergonomics. The interpreter is written in **Odin**.

**Phase 1 (current):** Tree-walking interpreter in Odin. Goal: nail syntax and type system.  
**Phase 2 (future):** Compiler targeting bytecode VM, manual memory management + optional GC.

Do not design toward Phase 2 until Phase 1 syntax and types are stable.

## Architecture

```
src/
  main.odin         # CLI: parse args, dispatch to run/repl/check
  lexer.odin        # Source → Token stream (hand-written)
  parser.odin       # Token stream → AST (recursive descent)
  ast.odin          # AST node types (tagged unions)
  types.odin        # Type definitions, inference, unification
  interpreter.odin  # Tree-walk eval (Env + call stack)
  value.odin        # Runtime Value union (Int, Float, Bool, Str, Struct, Enum, Fn, ...)
  error.odin        # Myr_Error: source span + message, pretty-printed
tests/
  *.myr             # Myr source files used as integration test fixtures
```

The pipeline is strictly linear: Source → Lex → Parse → Type-check → Interpret. No IR in Phase 1.

## Odin-Specific Implementation Notes

- AST nodes and `Value` are **tagged unions** (`union { ... }`). Use `#partial switch` when handling a subset of variants.
- Errors use multi-return: `(Value, bool)` or `(Value, Myr_Error)`. No exceptions.
- Use Odin's built-in `context.allocator` for all allocations — thread it through every procedure rather than using a global. This mirrors what Myr's own `context` system does, by design.
- `string` in Odin (`{data: ^byte, len: int}`) is the same mental model as Myr's `str` — slice views, not owned strings.
- `[dynamic]T` for growable arrays, `map[K]V` for hash maps — both allocator-aware via `context`.
- Environments (scopes) are linked lists with a parent pointer. Closures capture the env pointer at definition time.
- Span information (`Span :: struct { start, end: int }`) must be preserved from lexer through every AST node for error reporting.
- Type inference runs before eval; the interpreter can assume well-typed AST input.

## Language Design Decisions

These are **resolved** — don't revisit without explicit user instruction.

### Memory & Allocation
- Every function receives an implicit `context` argument carrying the current allocator (arena by default) and GC mode.
- Scoped override: `with_context({ allocator = my_arena }) { ... }`.
- `str` is a `{ptr, len}` slice view into arena memory. No owned String type. `cstr` only at C FFI boundaries.

### Types & Generics
- Generics use `[T]` square brackets, not `<T>`, to avoid parser ambiguity with comparison operators.
- `Array[T, N]` — fixed-size, stack. `Slice[T]` — `{ptr, len}` fat pointer. No special `[]T` syntax.
- Enum variants have **named fields only** — no positional tuple payloads.
- `soa` / `aos` are type-level qualifiers on struct types; field access syntax is identical either way.

### Modules & Build
- Directory = package (Odin-style). Files within a directory are organizational only; no explicit `mod` declarations.
- No package manager. The `myr` CLI drives builds. Build scripts are written in Myr itself (like Zig's `build.zig`).

### Metaprogramming
- Compile-time decorators (`@derive`, `@inline`, etc.) are the metaprogramming mechanism.
- `@runtime` opt-in generates runtime wrapper variants.

### C Interop
- Structs are C-ABI compatible by default — no marshaling needed at FFI boundaries.

### VM Instance Model
- The `VM` struct must have **no global state** — every piece of state lives inside the `VM` struct itself.
- Multiple `VM` instances must be safe to run concurrently on separate OS threads without any locking.
- Compiled bytecode (`Function` structs) is immutable after compilation and may be shared across VM instances read-only.
- Values do not cross VM boundaries by reference — they are deep-copied (primitives trivially, strings by bytes, structs by fields).
